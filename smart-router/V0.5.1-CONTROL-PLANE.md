# Hermes Smart Router v0.5.1 Control Plane

v0.5.1 is an additive governance and operations release on top of the v0.5.0 routing/safety path.

## Included P0–P2 capabilities

- Dynamic routing profiles: `fast`, `standard`, `strong`, `coding`, `vision`.
- Live upstream `/v1/models` discovery so OmniRoute route IDs are selected from the real deployment rather than invented.
- Powerful `/control/` panel (host default `http://127.0.0.1:8787/control/`) with routing, provider health, usage/cost telemetry, budgets, users, virtual keys, policies, knowledge, memory, agents, teams, plugins, audit and system health.
- RBAC with local users, scrypt password hashing, HMAC-signed stateless sessions and roles.
- Virtual API keys with tier allowlists, RPM/TPM/daily quotas and per-key monthly budgets.
- Budget scopes for global, user and team controls.
- Guardrail policy engine with role/team/tier/profile/prompt matching, deny actions, minimum-tier upgrades and output caps.
- Local first-class RAG/knowledge bases with chunking and lexical similarity retrieval; context is injected before the existing capability router evaluates the request.
- Persistent memory scopes: user, team, agent, project and organization.
- Reusable agent profiles and sequential/parallel agent teams with strong-tier synthesis.
- Plugin/tool registry for MCP/HTTP/webhook manifests. Registration does **not** auto-execute arbitrary remote tools.
- Immutable-style audit trail for security/admin actions plus route telemetry without storing raw prompts.
- PostgreSQL-ready shared control-plane storage and `SMART_ROUTER_HA_MODE=true`; HA mode disables node-local sticky routing to avoid replica divergence.
- v0.5.1 benchmark reporter for routing accuracy, false-fast rate, capability violations, measured cost and latency.

## Security defaults

The control plane is additive and disabled only when `SMART_ROUTER_CONTROL_PLANE_ENABLED=false`. OpenAI-compatible request authentication remains backward-compatible. Set `SMART_ROUTER_REQUIRE_AUTH=true` for production after creating virtual keys.

The `/control/` UI never embeds credentials. Authenticate using either a local panel user or `SMART_ROUTER_ADMIN_API_KEY`. Do not expose port 8080 directly to the Internet; use your existing private network/reverse proxy/TLS controls.

## OmniRoute mapping

v0.5.1 deliberately does not invent OmniRoute route IDs. Open **Control Plane → Routing → Discover upstream models**, then assign actual discovered IDs to fast/standard/strong/coding/vision. The mapping is persisted in the control database and takes effect without rebuilding the image.

## RAG request metadata

For auto-routed calls, attach internal metadata that Smart Router consumes and removes before forwarding:

```json
{
  "model": "auto",
  "messages": [{"role":"user","content":"Why is nginx failing?"}],
  "metadata": {
    "hermes": {
      "knowledge_bases": [1],
      "project": "production-k8s",
      "rag_limit": 4
    }
  }
}
```

The retrieved context is inserted before the existing router calls `decide()`, so context/capability gates see the augmented request.

## HA example

Set a strong `SMART_ROUTER_PG_PASSWORD`, then merge the supplied compose file:

```bash
docker compose \
  -f docker-compose.yml \
  -f smart-router/compose-ha-v0.5.1.example.yml \
  --profile smart-router --profile smart-router-ha up -d
```

For multiple router replicas, place them behind your reverse proxy/load balancer and use the shared PostgreSQL control database. HA mode intentionally disables local sticky-session state; a future Redis/shared sticky store can restore cross-replica stickiness without weakening consistency.
